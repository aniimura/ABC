★★★**2026-09-04、`git add <path>` だけでは足りないことを実測**(ABC3b)。
`git add lean/…/Section4.lean` としてから `git commit`(パスなし)したところ、
**別セッションが先に `git add -A` していた `Found/LocProP/PDerivate.lean` が
一緒にコミットされた**——`git add <path>` は「追加で何をステージするか」しか
決めず、`git commit` はパスを指定しない限り**インデックス全体**をコミットするため。
★まだ push 前・1 コミットのみだったので `git reset --soft HEAD~1` →
巻き込まれたファイルだけ `git restore --staged` → 取り直し、で復元できた
(これは「相手のコミット」ではなく「相手が未コミットのままステージしていたもの」
が自分のコミットに紛れ込んだケースなので、上の「歴史を書き換えない」の対象外
——書き換えたのは**自分の**直前コミットであり、相手のコミットには触れていない)。

**How to apply(追加)**: `git add <path>` の後は **`git commit -m "…" -- <path>`
のように commit 自体にもパスを渡す**。`add` だけでなく `commit` 側でも
限定して初めて、ステージ済みの他人のファイルを除外できる。

★★★**同日、追記——上の reset は結果的に危険だった。** `git reset --soft HEAD~1`
した直後、**別セッションがその「巻き込まれたコミット」の上に既に新しいコミットを
積んでいた**(ローカル ref は共有なので、push 前でも相手からは見える)。
気づかずに reset を続けていたら相手の1コミットを消すところだった。
★★幸い、その別セッション自身が非 fast-forward を検知し、**マージコミットで
両者を合流**させてくれた(内容衝突は「新しい方を採用」で解決)。
**結論: push 前でも「自分のローカルコミット」は他セッションから見える/積み増される
可能性があるので、[[parallel-session-sweeps-my-files]] 本文の「歴史を書き換えない」を
文字通り守るべきだった。** 気づいた時点で reset ではなく、次のコミットで
「本体は `<sha>` にある」と書く方に倒すこと。事故が起きても、慌てて
`git merge`/`git merge --abort` を連打するより、まず `git log --oneline --graph -10`
と `git status` で今どちらのセッションが何を触っているかを確認するほうが安全。

★★★★**2026-09-03、ABC3c が実測**——巻き込まれた側が `git commit --amend` で
自分のコミットから巻き込んだファイルを除去したところ、**push が非 fast-forward
で拒否された**。原因: amend は同じ `.git`(共有ワークツリー)の HEAD を即座に
書き換えるので、その上に自分が積んだ次のコミットが、まだ push していない
origin の(amend 前の)コミットと**祖先関係を失う**。

**How to apply(追加)**:
- 拒否されたら **force push しない**。`git fetch origin master` → 差分を見る →
  `git merge origin/master`(rebase より安全——他人のコミットを書き換えない)。
- 衝突するのはたいてい「巻き込まれたファイルそのもの」1 本だけ
  ——**内容がより新しい/完全な側**(`.src` を足した後など)を採用してよい
  (履歴の書き換えではなく、通常の3-way マージの選択)。
- 予防策の本命は上の「`git commit` にもパスを渡す」だが、**それでも巻き込みが
  起きた後に相手が amend すると、この非 fast-forward は避けられない**。
  マージで合流すればよく、動揺する必要はない。
