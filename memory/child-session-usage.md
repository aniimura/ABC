★2026-08-18、利用者の問い「子をどのタイミングで使うか」に答えて測ったこと。

## ★使うタイミング —— 仕様が確定してから

★**探索中は分割できない。** `Proposition 4.1` も `Theorem 3.4, (ii)` も、着手時点では
証明の形が分かっておらず、作業中に見つけた
(「(iv) と (v) の単系層が同一」「`irredNonPreStep` が `irredBounded` に書き換わる」)。
★★**前の一手の結果を見てから次の形が決まる間は、親が 1 本で進めるほうが速い。**

★**仕様が固まった瞬間が渡し時**である。判定基準は 2 つ:
1. 達成条件が 1 文で書けるか
2. 成否が**機械で**判定できるか(`lake build` / `node tools/check.mjs`)

## ★向く仕事

| 仕事 | 理由 |
|---|---|
| 仕様確定済みの長い機械的構成 | 例: `HomBirat` の移送。仕様確定・`lake build` で判定可 |
| `1_Structured` の逐語セクション | ゲートが逐語照合するので判定が機械的 |
| 反例探索(例 `pairing-vanishes`) | 当たらない試行が大量に出る。親の文脈を汚さない |
| REPL 起動待ちの並走 | `lean_start` に 130〜170 秒、`lake build` は競合時 316 秒かかった実績 |

## ★★このプロジェクト固有の制約 —— 子に git を触らせない

★**ワークツリーを ABC3b と共有しており、あちらは `git add -A` を使う。**
実測(2026-08-18)では、親のコミットが何度も ABC3b のコミットに巻き取られた。
★★**3 人目の書き手を入れると `index.lock` 衝突とコミット混線が悪化する。**

★したがって子には次を厳守させる:
- **git 操作を一切させない**(commit / push は親が行う)
- **新規ファイルだけを書かせる**(既存ファイルは import 1 行の追記まで)
- `lake build` は競合するので投げっぱなしにせず `wait_for_child` で待つ
- `sorry` を使わせない(使うならその宣言ごと消して、足りないものを報告させる)

**Why:** 子は文脈を分けられるが、**同じディスクを共有している**。
分けられるのは文脈であって、ファイルシステムではない。

**How to apply:** 渡す前に「達成条件 1 文」と「機械判定の手順」を書けるか自問する。
書けないなら、まだ親が探索する段階である。
