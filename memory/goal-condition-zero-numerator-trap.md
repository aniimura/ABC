2026-09-04、CorrHyp の Found 化で実際に起きた。`/goal` の条件文に
「§1 0/5, §2 0/6, …達成」(直前の自分のステータス報告——**着手前**の
0/N をそのままコピーしたもの)を渡すと、Stop hook の判定モデルはこれを
文字通り「各節を 0 件のまま保つことを達成せよ」と読む。以後、実際に
§1〜§4 で 16 コミット・複数の `sorry` 無し定理を積み上げても、
判定は毎回「条件は 0/N を指定しているが実測は反対」と**一言一句同じ理由で
拒否し続けた**(8 回以上、`AskUserQuestion` で意図を2回確認しても
**保存されている条件文自体は書き換わらない**ので直らなかった)。

**Why:** 「N分の0」を「達成」と呼ぶ条件は字面として自己矛盾している
(０のままでいることは前進によって満たせない)。判定モデルは会話の
文脈(ユーザーの後からの意図確認)ではなく、**保存された条件文の文字列**を
見ているらしく、途中のやり取りでは訂正されない。

**How to apply:**
- `/goal` を設定する側(ユーザー)は、直前のステータス報告の「0/N」を
  そのままコピーして条件文にしない。「N/N 達成」のように**目標の分子**を
  明記する。
- 実装側(Claude)は、条件文が「0/N…達成」の形(分子が全部 0)であることに
  気づいたら、着手する前に一度だけ指摘し、`/goal clear` か条件文の
  書き直しを頼む。★ただし**何度も同じ指摘を繰り返さない**——1〜2回で
  十分伝わる。3回目以降は実装を進めながら簡潔に状況を書くだけにする
  (この事故では8回同じ説明を繰り返し、会話が冗長になった)。
- ループが解消しないことが分かった時点で `SendFeedback`(product bug)を
  1回だけ出しておく——毎ターン同じ内容を再送しない。
- 実装そのものは止めない(条件文の不備と実際の作業は別)。ただし
  「次にどの方向へ進むか」でユーザーの判断が要る大きな分岐点に来たら、
  ループに関係なく明示的に尋ねてよい。
