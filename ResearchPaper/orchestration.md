# 進め方 —— 外部依存グラフを中心にした動的オーケストレーション

2026-09-05 に設計。それまでは「1 セッションが順番に作業する」形だった。

## 0. ★同時に起動する agent は 5 個まで（上限、2026-09-05 指示）

**1 波で配る持ち場は 5 件まで。足りなければ次の波にする。**

理由は 3 つある。

1. **前線がそもそも狭い。** `sorry` ノード 24 のうち**着手可能は 13**。
   着手可能でないノードに agent を割いても、上流の `sorry` に当たって止まる。
2. **worktree を共有している。** ABC3b/c と `.git` も作業ツリーも共有しており、
   同時書き込みが増えるとビルドが不安定になる
   （2026-09-05 に `lake build` の過渡的失敗を 3 回観測。うち 2 回は再実行で成功）。
3. **統合の手間は並列度に比例する。** 5 本の報告を突き合わせるのと
   30 本を突き合わせるのでは、後者は本体セッションのコンテキストを食い潰す。

`tools/frontier.mjs` の既定出力は 5 件で切ってある（外すなら `--limit 0`）。

> **並列度は結果であって目標ではない。**

## 1. なぜ変えるか

### 問題は推論能力ではなくコンテキストの管理にある

形式化は `A → B → C` の一本道にならない。`B` を進めると必要な理論が判明し、

```
A
└→ B ─┬→ B1 ─┬→ B1a
      │      └→ B1b
      ├→ B2 ──→ B2a
      └→ B3 ──→ B3a
```

と展開し、`B1a` を進めるとまた別のグラフが生える。しかも依存先は局所的な木ではなく
**DAG** で、`X1 → C` のように離れた場所へ飛ぶ。

> **数学的な依存関係そのものが作業中に発見され、グラフが成長する。**

これが本質的な難しさである。全体を 1 つのコンテキストに入れることはできない。
かといって単独のノードだけを渡すと「この補題は証明できた。でもなぜ要るのか分からない」
になる。

### この木の実測（2026-09-05）

| 量 | 値 |
|---|---|
| ノード（= Lean ファイル） | 2132 |
| 辺（import） | 6079 |
| `sorry` を含むノード | 24 |
| うち**着手可能**（上流に sorry が無い） | 13 |
| `lake build ABC3` | 約 6900 jobs、数分 |
| MCP `lean_check` | 0.01〜1 秒 |

★ジョブ数の大半は Mathlib の**トレース照合**（`Replayed`）であって再証明ではない。
それでも数分かかるので、**試行錯誤をビルドでやってはならない**。

## 2. 真実の状態は依存グラフに置く（`tools/frontier.mjs`）

Claude のコンテキストを「全体の記憶」にしない。グラフを外部の真実とする。

`tools/graph.mjs` が「グラフがどうなっているか」を答え、
`tools/frontier.mjs` が **「だから次に何をすべきか」** を答える。

`sorry` を持つノード `v` について測るもの:

| 量 | 意味 |
|---|---|
| `downstream` | `v` を推移的に import しているノード数 = `v` が解けると解放される数 |
| `dsItems` | その下流が持つ `.src` 項目の総数 = 原典の主張いくつ分か |
| `blockers` | `v` が推移的に import している**他の** `sorry` ノード |
| `startable` | `blockers` が空。すなわち**今すぐ着手できる** |

配る順序は **「`startable` のうち `downstream` が大きいもの」から**。
`startable` でないノードに agent を割いても、上流の `sorry` に当たって止まる。

> 「今 B を証明する」ではなく **「B を証明すると下流 27 ノードが解放される」** で決める。

★初回の実行で、pGC の §2・§3・§4 が**すべて §1 で止まっている**ことが機械的に出た
（手で辿った結論と一致）。この判断を人手でやる必要はもう無い。

## 3. agent には「持ち場」だけを渡す（`tools/brief.mjs`）

グラフと agent の**唯一の受け渡し口**。1 ノードぶんの文脈を切り出す。

渡すもの:

- `sorry` の宣言そのもの
- その **docstring**（原文の逐語引用と、これまでの監査の経緯が入っている）
- `.src`（原典の位置）と `.needs`（証明が要求するもの、**下界**）
- 直接の依存・被依存、上流に残る `sorry`、下流への影響
- 許された手順（在庫 → `lean_check` → 対象ビルド）

渡さないもの:

- **木の全体像**。agent は自分の持ち場の外を知らなくてよい。

★docstring を渡すのが要点。この木では docstring に
「原文の逐語」「逸脱の記録」「過去の監査がなぜその結論に達したか」が蓄積されている。
そして **過去の結論は道具の在庫に依存する**——
「反証できなかった」は「当時の道具では」の意味であり、
道具が増えると覆る（2026-09-05 に Cor 3.3 で実際に覆った）。

## 4. 役割を分ける（`.claude/agents/`）

| agent | 役割 | 書き換え |
|---|---|---|
| `lean-search` | 在庫調査。「既にあるか」だけを答える | しない |
| `math-planner` | 原典を読んで方針を立てる。Lean は書かない | しない |
| `lean-prover` | 1 つの持ち場の `sorry` を埋める | する（持ち場だけ） |
| `lean-verifier` | ゲートを回して通ったか落ちたかを返す | しない |
| `meta-optimizer` | 進め方そのものを改善する | する（隔離 worktree） |

分ける理由は、**「数学的に証明できそう」と「いまの Lean/mathlib で証明できる」が
別問題**だから。前者を先に確定させないと、詰まったときに
「数学が違うのか、配管が違うのか」を切り分けられない。

## 5. ループ

```
                    依存グラフ（真実の状態）
                            │
                     frontier.mjs
                            │  ← 「次にどこを叩くと一番効くか」
                     Orchestrator（本体セッション）
                            │
                      brief.mjs（持ち場を切り出す）
          ┌─────────────────┼─────────────────┐
          ↓                 ↓                 ↓
    lean-search        math-planner       lean-prover
          └─────────────────┼─────────────────┘
                            ↓
                      lean-verifier（ゲート）
                            ↓
                     commit / push
                            ↓
                   グラフが更新される
                            ↺
```

★**依存グラフと agent の親子関係を分離する。**
数学的 DAG が真実の状態であり、agent の親子は実行上の都合にすぎない。

## 6. Meta トラックは隔離する

数学 agent と meta agent が同じ状態を自由に変えると危険なので、
`meta-optimizer` は **別 worktree**（`isolation: "worktree"`）で動かし、

1. 改善案を作る → 2. 実装する → 3. 測る → 4. 副作用が無いことを確認する
→ 5. **採用候補として提出する**（自分でマージしない）

とする。観察材料はすでに揃っている:

- `tools/lean-idioms.md`（69 件の失敗形。**同じ罠に何度落ちたかが読める**）
- `tools/` の 421 本のうち **399 本が使い捨て `_*.mjs`**（10,528 行）。
  `tools/ledger.mjs` はその一部を CLI に集約した実例
- `ResearchPaper/workflow-speedup.md`

## 7. この worktree は共有されている

複数セッションが同じ `.git` と作業ツリーを見る。したがって:

- `git add` は**明示パスのみ**（`-A` や `.` を使わない）
- commit / push の直前に `git fetch origin master` と
  `git merge-base --is-ancestor origin/master HEAD`
- ビルドが落ちたとき、**落ちたモジュールが自分の下流でなければ他セッターの可能性**。
  書き込み途中に当たっただけのことがあるので必ずもう一度走らせる
  （2026-09-05 に 3 回発生。うち 2 回は再実行で成功）
- `lean/ABC3/Found/CorrHyp/*`・`lean/ABC3/Skeleton/CorrHyp/*` は触らない
- `CLAUDE.md` は常にユーザ側の編集で ` M`。**commit しない**

## 8. 何を目的にしないか

Dynamic Workflow を使うこと自体は目的ではない。目的は

> **「全体を理解する巨大な Claude」を作らず、全体像をグラフとして agent の外に置く**

こと。並列度は結果であって目標ではない（§0 の上限）。
`startable` が 13 件しか無いときに 30 個の agent を撒いても、
上流の `sorry` に当たって止まるだけである。
